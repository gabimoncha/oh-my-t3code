# omt commands

Every command accepts `--help`. Each command prints text for people. The commands that report state, such as `omt doctor`, `omt roles`, `omt defaults`, and `omt detect`, also print JSON with `--json`. `omt install`, `omt uninstall`, `omt worktree setup`, `omt defaults use`, and `omt detect --write` show the change first and ask before they write, or take `--yes`. `omt init` and `omt config init` do not ask. They create missing files and keep an existing config, with two exceptions: `omt init` adds missing lines to an existing `.omt/.gitignore`, and `omt config init --force` replaces an existing user config. The [spec](spec.md) describes each command in detail. In a project install without `omt` on `PATH`, run the commands as `.omt/bin/omt`. The [install guide](install.md#install-the-cli) lists the other ways to run omt, such as `npx omt` after a dev-dependency install and `npx omt3` for a one-shot run. Use `npx omt` only in a project that has omt as a dev dependency. Outside such a project, `npx omt` downloads a different npm package named `omt`. For a one-shot run, use `npx omt3`.

| Command | What it does |
| --- | --- |
| `omt install` | Installs the skills, the links, and the starter config. It shows its plan and asks before it writes. `--yes` skips the question, and `--dry-run` writes nothing. `--hooks` adds the Claude Code hook. `--project` installs into the current project and prints the worktree setup state of the current checkout. The plan shows the harnesses that omt detects (Claude Code, Codex), and a new config gets a `"harnesses"` key when one is missing. `--capabilities <file>` takes the saved output of the T3 tool `orchestrator_capabilities` for this detection; without it, omt reads the T3 settings and `PATH`. When the bundle no longer ships a skill that an earlier install wrote, such as `omt-loop`, `omt-review`, or `omt-show`, the install removes that skill folder and its links, and the plan shows `remove <name> (no longer shipped)`. It never removes a folder that omt did not install. An edited retired skill stops the install; `--force` backs it up and removes it. |
| `omt uninstall` | Removes what `omt install` added. `--project` removes the project install. |
| `omt update` | Updates the CLI with the command of the channel that installed it, then syncs the skills in user scope and in each recorded project. A skill that you edited stays, and the output names it. A managed skill that the bundle no longer ships is removed with its links, as in `omt install`. It shows its plan and asks before it writes. `--yes` skips the question, `--dry-run` writes nothing, and `--check` prints the current version, the latest version, the channel, and its update command, and writes nothing. `--skills-only` syncs the skills with the CLI that runs now and uses no network. `--project` updates only the current project. The `defaults` pin moves only when you answer yes to its own question. See [Update omt](install.md#update-omt). |
| `omt doctor` | Checks the runtime, the config, the default set, the harnesses, the skills, the links, the hook, `PATH`, and T3. A managed skill that the bundle no longer ships gives the warning `no longer shipped: <names> in <agents root>; run omt install`. `--project` checks the project install and the worktree setup of the current checkout. |
| `omt init` | Creates what is missing in `.omt/`: the starter config, `plans/`, and `.gitignore`, which ignores `plans/`, `grills/`, and the other live state. It adds the missing lines to an existing `.gitignore` and keeps an existing config. Then it prints the worktree setup state of the current checkout. |
| `omt config show` | Prints the merged config before omt applies the profile. `--defaults` prints the selected default set. |
| `omt config explain` | Prints the layer that sets each value: the default set, the user config, the project config, or a profile and the file that declares it. Below a value, an `over` line names each lower layer that the value overrides. `--profile <name>` explains that profile instead of the selected one, and `--json` prints the report as JSON. See [See where each value comes from](configuration.md#see-where-each-value-comes-from). |
| `omt config edit --web` | Starts a local editor for the user config and the project config, and opens it in the default browser. `--no-open` only prints the URL. Before each write, the page shows the diff and the config check. A write keeps the comments of the file, and it fails when it adds a config error or when the file changed on disk. The editor runs on 127.0.0.1 until you press Ctrl-C or close its tab. See [Edit the config in a browser](configuration.md#edit-the-config-in-a-browser). |
| `omt config path` | Prints the paths of the user config and the project config, and whether each exists. |
| `omt config validate` | Reports problems in both config files and in every profile. Exits 1 on an error. |
| `omt config init` | Writes the starter user config. `--force` overwrites an existing file. |
| `omt defaults` | `list` prints the dated default sets and marks the latest and the selected set. `diff [<from>] [<to>]` prints what changes between two sets and which config file overrides each change. `use <set\|latest>` sets the `"defaults"` key of one config file and changes nothing else; it takes `--user`, `--project`, `--dry-run`, and `--yes`. See [Pin the default set](configuration.md#pin-the-default-set). |
| `omt detect` | Prints which harnesses (`claudeAgent`, `codex`) can run child tasks, the `"harnesses"` value that fits, and its effect on the roles. `--capabilities <file>` uses the saved output of `orchestrator_capabilities`. `--write` sets or removes the `"harnesses"` key of one config file; it takes `--user`, `--project`, `--dry-run`, and `--yes`. See [Match the harnesses on your machine](configuration.md#match-the-harnesses-on-your-machine). |
| `omt roles` | Prints how every role resolves. |
| `omt route <role>` | Prints the `delegate_task` arguments for one role as JSON. `--against <provider\|driver\|auto>` names the worker that a cross-family role reviews. |
| `omt brief <role> --task <text>` | Renders a brief. `--save --json` saves the brief and returns a short dispatch task and a ledger command. |
| `omt profile` | Lists the profiles. `show [<name>] [--plan <slug>] --json` shows the resolved workflow settings. |
| `omt lock` | Runs a command under a shared build lock, or lists the held and free locks. |
| `omt git` | `check <commit\|push\|pr\|merge> [--user <login>] [--host <host>] [--pr-author <login>] [--plan <slug>] [--profile <name>] [--json]` prints `auto`, `ask`, or `off` with the reason, from the profile's `workflow.git` policy and the current and default branch. It writes nothing. |
| `omt plan` | Creates plan files and shows their progress. `new --profile <name>` selects a profile, and `new <slug> --light` leaves out the oracle item. `profile <slug> <name\|none>` switches the profile. `mark <slug> <id> <done\|open\|blocked>` marks one item. `limit <slug> <n\|none>` sets or removes the plan's parallel limit. A run has no task budget, so `--tasks` and `--max-tasks` fail with a usage error. `status <slug>` prints the next item, the `ready:` units, and a `warning:` line for each dependency that names no unit or names its own unit. It also prints one warning for the first dependency cycle only. It also warns about a `max-tasks` header key, which has no effect. |
| `omt ledger` | Records and counts the delegated tasks in `.omt/ledger.jsonl`. A result entry with a terminal status, such as `completed` or `failed`, closes the dispatch that has the same `--task-id`. Without a task id, it closes the dispatch with the same plan, unit, role, round, and attempt. `stats` prints `can dispatch: yes` while fewer than `maxParallel` tasks are active; the number of tasks that a run started never stops a dispatch. |
| `omt worktree` | `check` (the default) reports the current checkout's package manager, lockfile, linker settings, `t3.json` setup script, and the T3 activation step. It writes nothing and starts no process. `setup [--dry-run] [--yes]` writes a missing `t3.json` and `.t3/omt-worktree-setup.mjs` for a Bun or pnpm project, and for pnpm a missing `pnpm-workspace.yaml` with `enableGlobalVirtualStore: true`. The runner installs dependencies into a global virtual store before the agent starts. Neither subcommand rewrites an existing file. In a linked worktree, the files go into that worktree. |
| `omt paths` | Prints the absolute paths of the project root, `.omt`, the plans, the grills, the ledger, the evidence directory, the project config, and the shim. In a linked git worktree, the paths point into the main checkout. `--json` prints them as an object, and `--grills` prints only the grills directory. |
| `omt help [<command>]` | Prints the command list, or the help of one command. It prints the same text as `omt --help` and `omt <command> --help`. |
| `omt hook user-prompt-submit` | Runs the Claude Code hook. The hook calls this command. You do not run it. |

`omt route` and `omt brief --json` take `--against <provider|driver|auto>` for a cross-family role. A provider id or a driver kind names the worker whose change the role reviews. `auto` reads that worker from `.omt/ledger.jsonl` and needs `--plan <slug>`.

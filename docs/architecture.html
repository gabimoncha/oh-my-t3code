oh-my-t3code architecture

oh-my-t3code (omt) is a zero-dependency TypeScript CLI plus a set of skills. It adds role-routed multi-agent orchestration on top of the T3 Code orchestrator v2 MCP tools.

1. What it is and who it is for

The user is a developer who runs Claude Code, Codex, Cursor, Pi, or OpenCode agents from T3 Code. That developer types one sentence, for example ulw: add OAuth to the API. omt turns the sentence into a planned run. Each unit goes to the right model and gets a review from the other model family when that family is available. The run ends with tests that ran. In a HEAVY run with the default profile, a reviewer from the other model family tries to find faults in the result before the run counts as done.

ulw is the keyword that starts the omt-ulw skill. Terms such as unit, rung, wake, and oracle are defined in the glossary.

The maintainer gets a small TypeScript CLI with no runtime dependencies, 11 portable skills, and one config file. omt adds no server, no daemon, and no T3 fork. Every subagent is a T3 child thread, so the T3 UI already shows progress, cancellation, and results.

The split in one line.

T3 gives the mechanism. It does not give roles, model routing, briefs, review loops, done criteria, or fan-out limits. omt fills these gaps and uses only the t3-code MCP tools that T3 already exposes.

Read the table as a list of gaps. T3 gives the middle column. omt adds the right column.

2. The big picture

omt has two parts. The skills hold the judgment. The CLI does the deterministic work. Both run inside the parent agent's session. Only the skills call T3.

  • The skills are Markdown SKILL.md files. They plan, split work, read results, and choose the next step.
  • Three ways to start ulw. (1) On Claude Code with --hooks, the hook adds a pointer to the prompt. (2) On any driver, the model loads omt-ulw on its own, because the skill description holds the words ulw and ultrawork. (3) The user types a mention, such as /omt-ulw in Claude or $omt-ulw in Codex. The hook is optional. It only makes start (1) more reliable.
  • The CLI merges config, resolves role chains, maps effort to options, renders briefs, and counts plan items and ledger entries.
  • The CLI cannot call T3. Claude and Codex sessions get the MCP server through config, not through environment variables. So routing is unverified by default, and T3 checks the target at dispatch.
  • The skills also work without the CLI. They look for omt on PATH, then .omt/bin/omt, then follow the manual steps in roles.md and brief.md. They never call a runner such as npx themselves. A shim from a one-shot install calls its runner with the pinned version. Without the CLI, the conductor resolves roles with the table in roles.md, writes briefs by the layout in brief.md, edits the plan checkboxes and log by hand, and counts the open task ids in the plan's log in place of omt ledger stats.

3. Life of a ulw request

This is the main flow. The omt-ulw skill makes the parent agent a conductor. The conductor plans, dispatches, reads, and verifies. It edits no product files.

The steps of omt-ulw

The conductor prints the banner omt ultrawork: plan, delegate, review, test, verify. as its first line. Then it runs these steps in order.

  1. 0

    Check your mode. Call t3_thread_configuration with no threadId and read interactionMode. In plan mode, ask the user to switch to default mode, or offer omt-plan. Then run the branch check in delegation.md: it checks whether the current branch is behind the default branch.

  2. 1

    Frame. Write the objective in one sentence, the done conditions, the tier, and the plan slug. Each done condition is a check that can fail.

  3. 2

    Route. Run omt profile show --json (with --plan <slug> when the plan file exists) and keep the effective profile, workflow, limits, roles, and models. Then run omt roles --plan <slug> for the targets. Without the CLI, use the resolve-by-hand table in roles.md.

  4. 3

    Explore. Dispatch 1 to maxParallel read-only explore tasks with units E<k>, one narrow question each. End the turn. Skip this step when the code is already known.

  5. 4

    Plan. Run omt init when .omt/.gitignore is missing. LIGHT runs omt plan new <slug> --light. HEAVY runs the omt-plan skill, which returns here after plan review.

  6. 5

    Dispatch. For each ready unit, run omt ledger stats --plan <slug>, then omt brief <role> ... --json, then delegate_task, then omt ledger add --status dispatched. The record carries --provider and --model from the target of the call that T3 accepted. After a fallback, that is the fallback's target. End the turn.

  7. 6

    On wake. Call task_status for each task id. Record completed with the verdict, or failed. Check each DONE claim. Record rejected when the check disproves it.

  8. 7

    Review. Apply build.review. With every-round, dispatch a fresh review task per round. With first-round, review only the first round and send each fix round to step 8. With off, skip review. Build each review brief with --against auto, so the reviewer comes from the family other than the unit's worker. Pass the unit data in a --context-file, never the rendered execute brief. From round 2, pass earlier findings in --prior-file.

  9. 8

    Test. Apply build.verify. With every-unit, dispatch a verify task for every unit. With heavy, dispatch verify for each HEAVY unit; for a LIGHT unit, the conductor runs the verify commands itself and saves the output. After VERIFIED, apply build.qa. With planned, dispatch a qa task when the plan's ## Tests section has lines for the unit. With off, skip qa. When every required task returns VERIFIED, run omt plan mark <slug> <unit> done and record verified.

  10. 9

    Fix. Send the kept findings to a fix task in the next round. A ui unit uses ui in every round, and never falls back to another role or family. For other units, the fix is an execute fix, or a deep fix when a finding needs investigation: its cause is unknown, the previous fix failed for the same reason, or the fix changes the design. When the next round would pass maxReviewRounds (default 4), mark the unit blocked and ask the user.

  11. 10

    Final gate. The conductor runs every final check (F1, the full test suite, the typecheck) and marks D and F items. Then it applies build.oracle. heavy runs the oracle for HEAVY runs only, always runs it for both tiers, and off skips it. When the oracle is required, the conductor dispatches one oracle task with --unit F2 and --against auto, so the oracle comes from the family other than the main implementer's. It repeats until it returns APPROVE or maxReviewRounds stops it.

  12. 11

    Report. Tell the user what changed by file, each done condition with its evidence, the verdicts per unit, and the open items. Make one commit for the run, then push and open or update the PR, each as omt git check allows. Report the commit hash and the PR URL.

The active profile sets the switches in steps 7 to 10. A plan header can name a profile; otherwise the config's profile applies, and the default is normal. omt ledger stats prints the active name on its profile: line, and omt profile show prints the resolved values. The tier table and the examples on this page use normal.

4. Roles and routing

Skills and plans name a role, never a model. The config maps each role to an ordered chain of rungs. A rung is a provider or driver, a model, and an effort level. The first rung that T3 can run wins. A chain survives a missing subscription or a disabled provider.

Default roles (src/config/defaults.ts). Each rung reads provider / model / effort. Mode is interactionMode. Every role has runtimeMode inherit. The skill tries rung 1 first. It sends rung 2 only when T3 refuses rung 1. For a cross-family role, --against can put rung 2 first (see below).

Rung 1 and rung 2

Rung 1 is the target that the role tries first. Rung 2 is a backup. The skill sends rung 2 only when T3 refuses rung 1 with a typed error, for example provider_unavailable for a disabled provider. Rung 2 is not a second opinion. One task runs on one rung, never on both. For plan-review, review, and oracle, --against can change the order. When the worker ran on Codex, rung 2 (Opus) goes first, and rung 1 (Astra) becomes the backup. The rule does not change. One task runs on the first target, and the backup runs only when T3 refuses that target.

Every default rung sets provider equal to driver (claudeAgent or codex). These are the ids of the T3 built-in provider instances. So a default target names providerInstanceId, not only driverKind. The reason is observed T3 behavior. T3 checks a named provider instance again before it refuses it. T3 picks a driverKind-only target from a cached provider snapshot, and that snapshot can be stale.

Cross-family roles and --against

plan-review, review, and oracle have crossFamily: true. The reviewer of these roles comes from the family other than the worker's. The family is the driver (claudeAgent or codex), not the model.

omt route and omt brief take --against <provider|driver|auto>. The value names the worker whose change the task reviews. For a cross-family role, the CLI moves the rungs of the other family to the front. Each group keeps its configured order. So when Opus wrote the change, the review runs on codex/gpt-6-astra first. This is already the configured order, so no rung moves. When Luna, Sol, or Astra wrote it, the CLI moves claudeAgent/claude-opus-5-5 (configured rung 2) to the front (Figure 3). When the other family cannot run, the same family reviews. With --capabilities, the CLI finds this before dispatch and a note says so. Without it, T3 refuses the other-family target at dispatch, and the skill sends the same-family fallback.

  • --against auto reads .omt/ledger.jsonl and needs --plan. With --unit, when the unit has a work or plan dispatch with a provider, the worker is the provider of the last one. In all other cases, the worker is the provider of most units in the plan. This includes no --unit, and a unit with no such dispatch, such as the oracle unit F2. A tie goes to the tied provider with the latest dispatch. When the plan has no dispatch with a provider, the configured order applies.
  • Without --against, the configured order applies. The cross-family roles then start on Codex, which fits the default worker, execute on Claude.
  • On a role without crossFamily, --against has no effect, and a note says so.
  • The CLI reports its choice as notes. omt route puts them in notes. omt brief --json prints each one to stderr as note: <note>, so the JSON on stdout keeps its shape.

5. Briefs and result contracts

A child sees nothing of the parent conversation. T3 does not copy the history. So every task carries a self-contained brief. task_status.summary is the child's last assistant message. So every brief ends with a fixed result block that the parent can read.

The delegateTask payload

omt brief <role> ... --json wraps the brief in ready delegate_task arguments. This is the output of omt brief review ... --plan auth --unit U3 --round 2 --against auto --json with the default config and no --capabilities. The ledger shows that unit U3 ran on claudeAgent, so Astra reviews first.

Every default rung names its provider instance, so target uses providerInstanceId. T3 checks a named provider instance again before it refuses it, but it takes a driverKind-only target from a cached snapshot that can be stale. How the parent acts on a verdict

  • DONE is a claim. The parent checks the scope diff, runs at least one verify command, and reads the evidence file.
  • REQUEST_CHANGES sends the P0 to P2 findings to fix tasks.
  • BLOCK has two causes. A P0 finding with a clear fix inside the unit's scope goes to a fix task, as for REQUEST_CHANGES. A wrong approach, or a P0 whose fix changes the plan, marks the unit blocked, and the conductor re-plans it or asks the user.
  • INCONCLUSIVE is not a pass.
  • BLOCKED: read OPEN, resolve the blocker (a missing file, a scope change, or an owner decision), then dispatch again with the next attempt.
  • ESCALATE re-plans, moves the unit to deep, or asks the user.

Severity levels. P0 breaks the build, loses data, or opens a security hole. P1 is a wrong result in a normal path. P2 is a wrong result in an edge case, a named missing test, or a requested CRAP finding above 30. P3 is style or clarity.

6. State in the repository

A long run outlives the agent's context. So the run state lives in files under .omt/ in the project root. After compaction or a context reset, the conductor re-reads omt plan status <slug> and omt ledger list --plan <slug> before it acts.

Config layers

  • Each file is JSONC. Comments and trailing commas are allowed. A syntax error becomes one issue, and the loader skips that file. A missing file is not an error.
  • Root keys are $schema, version (must be 1), profile, profiles, models, roles, limits, and visuals. An unknown key is an error, and the loader drops it.
  • An existing role merges field by field. A new chain replaces the old chain as a whole. A new role needs description, access, and chain.
  • src/config/schema.ts builds the JSON Schema from the constants in validate.ts. bun run schema writes it to schema/omt.schema.json, and a test checks that the committed file matches.

The plan file

.omt/plans/<slug>.md is Markdown that people can read and omt plan status can count. Column-zero lines that match ^- \[( |x|X|~)\] (U|D|F)(\d+)\. (.*)$ are items. U is a unit, D a done-when check, F a final check. A shortened example from the template (the ## Summary, ## Research, ## Roles, and ## Tests sections are left out):

# Retry failed HTTP calls

<!-- omt-plan v1 slug=http-retry created=2026-10-06T09:00:00.000Z -->

## Objective

omt plan mark rewrites the checkbox, appends a log line, and writes the file atomically. A LIGHT plan (--light) has no F2 line. A plan is complete when items exist and every item is done.

The ledger

.omt/ledger.jsonl is append-only. Each entry is one JSON line, written with a single appendFile call. Fields are ts, role, status, and the optional plan, unit, round, attempt, taskId, clientRequestId, provider, model, verdict, and note.

{"ts":"2026-10-06T09:12:03.000Z","role":"execute","status":"dispatched","plan":"http-retry","unit":"U1","round":1,"attempt":1,"taskId":"<taskId>","clientRequestId":"omt:http-retry:U1:execute:r1:a1","provider":"claudeAgent","model":"claude-opus-5-5"}

Skills record --provider and --model on every dispatch. --provider is target.providerInstanceId, or target.driverKind when the target has no instance id. --model is target.model. Both come from the target of the delegate_task call that returned the task, so after a fallback they name the fallback. --against auto reads these fields to find the worker of a unit, or the provider of most units in the plan. A worker entry is a dispatched entry of a role whose result is work or plan. An entry without a provider does not count.

omt ledger stats computes the dispatch gate. canDispatch is active < maxParallel and dispatched < maxTasksPerRun. With --plan, a max-parallel key in the plan header lowers maxParallel to the lower of the two values, and a max-tasks key replaces maxTasksPerRun. omt plan limit <slug> <n> --tasks <n> sets both keys. Skills dispatch only while it prints can dispatch: yes.

$ omt ledger stats --plan http-retry
plan: http-retry
profile: normal
dispatched: 3
active: 1
terminal: 2
max parallel: 6
max tasks per run: 24
can dispatch: yes

A run is all ledger entries of one plan slug. The skills always pass --plan <slug>, so a new plan starts with a new budget of maxTasksPerRun. Without --plan, the counts cover the whole ledger.

When the output shows can dispatch: no and active: 0, no wake will come. The run is stalled, and the conductor tells the user which limit to raise.

Evidence

Edit children save command output and logs under <root>/.omt/evidence/. The brief says so in its evidence line. A LIGHT conductor that runs the verify commands itself saves the output there too. The report quotes the evidence for each done condition.

Why state lives in the repository.

The run outlives the agent's context, and compaction drops detail. Files survive both. omt init writes .omt/.gitignore with ledger.jsonl, evidence/, bin/, install.json, backups/, plans/, locks/, and guardrails.md, so the run data stays out of commits. All worktrees of one repository share the one .omt/ in the main checkout, so a thread in one worktree reads the plan that a thread in another worktree wrote.

The waiting model

Every write tool, delegate_task included, needs the caller's active turn. After the turn ends, writes fail with parent_not_active. The wake names only task ids. The normal path has five steps.

  1. The conductor dispatches async tasks.
  2. It records them in the ledger.
  3. It ends its turn.
  4. After the turn ends, T3 queues the wake as a new turn. A Claude parent never gets the wake inside a running turn.
  5. The conductor calls task_status for each task id.

Exception. When a goal or a stop hook keeps the turn running, the skill uses mode: "wait" for one task or t3_thread_wait for parallel tasks.

When task_status.summary is Child task completed without an assistant result., the child put its answer somewhere else, often in a proposed plan in plan mode. The conductor reads the child with t3_thread_read (view messages) before it dispatches again. A later wake that names tasks that the conductor already read needs no action.

8. Guardrails

T3 sets no cap on concurrent tasks or nesting depth, and every child can delegate again. omt sets its own limits and rules.

Limits in limits of the config
LimitDefaultRangeChecked by
maxParallel61 to 32omt ledger stats (active)

maxDepth10 to 3The delegation line in every brief
maxReviewRounds41 to 10ulw step 9, the oracle, omt-plan, omt-design, and the omt-review fix loop
  • Read-only roles run in plan mode. T3 enforces read-only access for plan-mode children on Claude, Codex, Cursor, and OpenCode. T3 has no plan-mode handling for Pi, and no default rung uses Pi.
  • A plan-mode thread dispatches only read-only roles. It dispatches only roles such as explore, research, plan-review, review, and oracle, writes no files, and gives the result in its final message. It runs no omt init, plan new, plan mark, or ledger add.
  • Children share the checkout. T3 Code v0.1.0 can isolate a child in a worktree, but omt does not use that yet. Every unit has an explicit scope. Editing units run in parallel only when their scopes do not overlap. Every brief tells the child never to break and restore files in the shared checkout. The qa role makes a failure proof in a private copy.
  • The conductor edits no product files. It stops and reports when no child can edit.
  • Reviewers come from the other family. plan-review, review, and oracle are cross-family relative to the worker. When the other family is not available, the same family reviews.
  • Modes only narrow. Runtime rank is approval-required < auto-accept-edits < auto < full-access. Interaction rank is plan < default.
  • Skills read modes with t3_thread_configuration. They must not call orchestrator_capabilities to read modes.

Hook skip rules

omt hook user-prompt-submit reads the prompt and decides whether to print the pointer. It always exits 0. It prints nothing on empty input, invalid JSON, a missing prompt, or no match.

  • It copies the skills with a .omt-managed.json marker.
  • It creates relative symlinks.
  • It writes a starter config.
  • It adds the hook when --hooks is given.
  • It keeps backups of the files that it changes.
  • It records a manifest.

The no-trace guarantee.

After omt install --project, with or without --hooks, git status --porcelain shows nothing new. The one exception is a settings.local.json that the repository tracks: it shows as modified while the hook is installed.

After omt uninstall --project, the tree and the exclude file are byte for byte as before the install, with these exceptions:

  • Data that the user created meanwhile (plans, ledger, evidence) stays, and so does what keeps it out of git: .omt/.gitignore and a reduced exclude block.
  • A reduced manifest stays when a created file stays. It records the created files that stay.
  • A file that the user edited after the install stays, with its block entry. An edited .omt/config.jsonc stays unless you add --purge.
  • An omt hook entry that was in the settings file before the install is removed, so a tracked settings.local.json shows as modified.
  • An existing skill that the install updated stays updated.
  • A backup that the uninstall could not restore exactly stays in .omt/backups/, hidden from git. A path that install --force replaced stays in .omt/backups/<stamp>/ and does not move back.

User scope and project scope never read or write each other's files. The install finds the exclude file without running git.

Out of scope

  • A T3 fork or a T3 plugin API. T3 has no plugin API, and omt uses only the surfaces T3 exposes.
  • A DAG scheduler, team mailboxes, memory, or computer use. T3 child threads and worktree threads cover the common cases.
  • Hooks for Codex, Cursor, and OpenCode. Codex hooks need per-hook trust. They are a later step.
  • Copied OmO code or prompt text. Its Sustainable Use License 1.0 does not allow it. omp and T3 are MIT.
Version 0.1 limits.

The ulw hook works only in Claude Code. No tool can set a T3 goal. The CLI cannot call T3. Children share the checkout. The family is the driver, not the model vendor, so a driver that runs models of several vendors (Cursor, OpenCode) counts as its own family.

12. Where to make a change

docs/spec.md is the contract. Change the spec first, then the code and the tests.

  • A new role. Add it to a config file. To ship it as a default, add it to src/config/defaults.ts and add a persona in skills/omt/references/roles/<role>.md.
  • A new command. Add a file in src/commands/ and register it in src/main.ts.
  • A skill change. Edit skills/<name>/SKILL.md. A test checks that every relative link in a skill resolves.

For each change, update docs/spec.md in the same change and run bun run verify.

13. Glossary

T3 orchestrator v2
The app-owned orchestration in T3 Code. Every provider session reaches it through the t3-code MCP server at /mcp.
delegate_task
The T3 tool that creates a child thread on a chosen provider and model. Its default mode is async.
wake
The fixed text that T3 queues into the parent when async children finish. It names the task ids, not the results.
interaction mode
plan or default. Plan mode makes most drivers read-only. A child can only narrow it.
runtime mode
approval-required < auto-accept-edits < auto < full-access. A child can only narrow it.
conductor
The parent agent that runs omt-ulw. It plans, dispatches, reads results, and verifies. It edits no product files.
role
An omt name for a kind of work, such as execute or review. It maps to a chain of rungs. In T3, the role argument is only a one-line prefix.
rung
One entry in a role chain. It names a provider or driver, a model, an effort, and optional raw options. The skill tries the rungs in order. A later rung is a backup that runs only when T3 refuses the earlier one. It is not a second opinion. For a cross-family role, --against can put a later rung first.
chain
An ordered list of 1 to 10 rungs. The first ok rung wins.
fallbacks
The targets of the later ok rungs, in the order tried. The skill uses them on typed T3 errors.
crossFamily
A role flag. For a role with crossFamily: true, --against puts the rungs of the family other than the worker's first. The defaults set it for plan-review, review, and oracle. omt roles shows it in the CROSS column.
--against
A flag of omt route and omt brief. Its value is a provider instance id, a driver kind, or auto. It names the worker whose change the task reviews. auto reads the worker from the ledger.
worker family
The driver of the worker, such as claudeAgent or codex. The family is the driver, not the model vendor.
effort ladder
off < minimal < low < medium < high < xhigh < max, mapped onto each driver's option.
mode ceiling
The parent's modes, which a child cannot widen. omt checks it only with capabilities.
verified / unverified
A route is verified when a saved orchestrator_capabilities result is passed with --capabilities. Otherwise T3 validates the target at dispatch.
persona
The role's instruction file, roles/<role>.md.
brief
The self-contained task text that omt renders for a child. The child sees nothing else.
omt-brief v1 marker
The first-line HTML comment of a brief. It carries role, round, depth, plan, and unit, and makes the ulw hook stay silent.
result block
The fixed final section of a child's last message. It starts with STATUS, VERDICT, ANSWER, or PLAN.
clientRequestId
The idempotency key omt:<plan>:<unit>:<role>:r<round>:a<attempt>.
round / attempt
The round increases with each review or fix round. The attempt increases with each retry or fallback rung in a round.
depth / maxDepth
The child's delegation level and the maximum level. At the maximum, the child does the work itself.
unit
A unit of work. In a plan file, a U<n> item with a role, scope, done condition, verify command, and dependencies. As a --unit value in the ledger and request ids, also E<k> (explore), G<k> (review group), Q<k> (research question), and F<k> (review fix).
U / D / F items
Plan checkboxes for units, done-when checks, and final checks (F1 test suite, F2 oracle).
LIGHT / HEAVY
The two ulw tiers. LIGHT is one or two units in one area with no design decision left. HEAVY is everything else.
ledger
.omt/ledger.jsonl. It records the delegated tasks, rounds, and verdicts.
ledger slot
A dispatched entry that no terminal entry has closed. It counts as active.
run
The work of one plan slug. maxTasksPerRun and maxParallel count the ledger entries of that slug.
canDispatch
active < maxParallel and dispatched < maxTasksPerRun.
P0 to P3
Review severity levels, from a broken build or security hole (P0) to style (P3).
oracle
The read-only role that reviews the finished change from the family other than the main implementer's before a run counts as done, when build.oracle requires it. With normal, that is every HEAVY run.
frozen blocker list
The round 1 plan-review blockers, written under Log. Later rounds count only those, regressions, or cited risks.
shared checkout
A delegated child runs in the parent's project, branch, and worktree. It is not isolated. T3 Code v0.1.0 can isolate a child with isolation: "worktree", and omt does not use that yet.
track
An omt-swarm unit that runs as a top-level T3 thread in its own worktree and ends in a PR.
tick
One omt-loop iteration, recorded in the ledger with role loop.
pointer
The additionalContext text that the ulw hook injects. It tells the agent to load omt-ulw first.
shim
<root>/.omt/bin/omt, a sh script that runs the CLI that made the install: the recorded binary, the recorded runtime with the recorded CLI file, or a one-shot runner with the pinned version.
exclude block
A per-root section in the repository's info/exclude that hides a project install from git.
managed directory
A skill directory that holds .omt-managed.json with package, version, skill, and hash.
locally modified
A managed skill whose current hash differs from its marker hash. Install treats it as a conflict.
OmO
oh-my-openagent. Source of categories with fallback chains, ultrawork, plan review rounds, and evidence-based done. Sustainable Use License 1.0.
omp
oh-my-pi. Source of model roles, agent definitions, fan-out with shared context, and the review recipe. MIT.
